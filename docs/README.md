# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в доме
- Система поддерживает включение/выключение отопления
- Система поддерживает установку температуры

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру
- Система поддерживает получение данных о температуре с датчиков
- Система поддерживает хранение данных о температуре

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go.
- База данных: PostgreSQL.
- Архитектура: Монолитная.
- Взаимодействие: Синхронное
- Масштабируемость: Ограничена.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Домен 1: Управление устройствами

- Поддомен: Управление реестром устройств
- Контекст: Информация о датчике
- Границы: handlers/sensor.go (CreateSensor, GetSensors, GetSensorByID, UpdateSensor, DeleteSensor), models/sensor.go(SensorCreate,Sensor,SensorUpdate) , db/db.go (CreateSensor, GetSensors, GetSensorByID, UpdateSensor, DeleteSensor)

- Контекст: Информация об исполнительных устройствах (нет в коде)

---

- Поддомен: Управление состоянием устройств
- Контекст: Состояние датчика
- Границы: handlers/sensor.go (UpdateSensorValue), db/db.go (UpdateSensorValue)
- Контекст: Управление отоплением (нет в коде)

---

Домен 2: Телеметрия

- Поддомен: Сбор телеметрии
- Контекст: Получение показаний с датчиков
- Границы: handlers/sensor.go (GetSensorByID), services/temperature_service.go (GetTemperatureByID, GetTemperatureByLocation), models/sensor.go (Sensor, TemperatureResponse)

### **4. Проблемы монолитного решения**

- низкая отказоустойчивость: Отказ внешнего сервиса temperature-api приводит к отказу всей системы
- высокая связанность компонентов: Изменение формата ответа от temperature-api или добавление новой функциональности в обработку показаний может неожиданно повлиять на код регистрации датчиков, несмотря на отсутствие прямой зависимости между ними.
- сложность тестирования: Для написания юнит-тестов отдельного компонента требуется запустить всю инфраструктуру: PostgreSQL, монолит, mock temperature-api
- единая база данных: При росте количества датчиков одновременные операции могут создавать блокировки
- отсутствие независимого развёртывания: Обновление кода получения показаний требует перезапуска всего монолита, что приводит к временной недоступности всей системы и прерыванию обслуживания пользователей.
- неэффективное масштабирование

# Задание 4. Создание и документирование API

### 1. Тип API

AsyncAPI может применяться для взаимодействия между сервисами через события, например при поступлении новой телеметрии, запуске сценариев. REST API используется для синхронных операций, например, получения данных об устройствах, обновления конфигурации, создания сценариев. Для документирования в формате OpenAPI выбраны синхронные запросы (REST API).

1. `/devices/{deviceId}`
2. `/devices/{deviceId}/commands`
3. `/scenarios`
4. `/scenarios/{scenarioId}`

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1. сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2. Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3. Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
